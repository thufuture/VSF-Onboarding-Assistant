# P2 — API + state machine nhân viên (chi tiết)

> Thuộc [ke-hoach-trien-khai-portal.md §5](../ke-hoach-trien-khai-portal.md) (P2). Dựa trên model/migration đã có ở [P1](../P1/P1.md). Định nghĩa chính xác state machine trước khi code, tránh sửa lại thuật toán giữa chừng (đúng tinh thần P0A D8 "khó đảo ngược").

## 1. Phạm vi

- **Có:** tự động tạo `EmployeeJourney`/`EmployeeTask` từ 1 `JourneyTemplate` đã `PUBLISHED` khi nhân viên xem lộ trình lần đầu (chưa có bước "HR gán journey" riêng — để P4B/P3 làm UI thật); tính `READY`/`LOCKED` theo `TaskDependency` (chỉ AND, P0A D8); API `GET /me/journey`; API `POST /me/tasks/{id}/complete` (nhân viên tự bấm "Hoàn thành" — P0A D1).
- **Không có ở P2:** API `start` riêng (không cần — theo P0A D1, "Hoàn thành" là hành động duy nhất, không có bước "bắt đầu" tách rời); HR gán journey thủ công qua UI (P4B); ticket/Viga (P5/P7); nhiều journey cùng lúc cho 1 user (MVP: 1 user có tối đa 1 `EmployeeJourney` đang hoạt động).

## 2. State machine — quy tắc chính xác

Trạng thái hợp lệ: `LOCKED, READY, IN_PROGRESS, WAITING_EXTERNAL, BLOCKED, DONE, SKIPPED` (đã bỏ `NOT_APPLICABLE`/`WAITING_APPROVAL` — P0A D1/D4). P2 chỉ chạm 3 trạng thái: `LOCKED`, `READY`, `DONE` — các trạng thái còn lại (`IN_PROGRESS`, `WAITING_EXTERNAL`, `BLOCKED`, `SKIPPED`) để dành cho khi có Viga/ticket (P5/P7), P2 không có API nào set chúng.

1. **Khởi tạo journey:** với mỗi `TaskTemplate` thuộc `JourneyTemplate`, tạo 1 `EmployeeTask`. Task **không có `TaskDependency` nào** → `READY` ngay. Task **có** `TaskDependency` → `LOCKED`.
2. **Hoàn thành 1 task:** chỉ hợp lệ khi task đang `READY`. Set `DONE` + `completed_at`. Gọi lại là `DONE` → **idempotent, trả 200** (không lỗi — v14 §17 "API thay đổi trạng thái phải idempotent khi hợp lý"). Đang `LOCKED` → 409 `TASK_LOCKED`.
3. **Mở khóa tự động:** sau khi 1 task `DONE`, xét mọi `EmployeeTask` khác trong cùng journey đang `LOCKED`; với mỗi task đó, lấy toàn bộ `TaskDependency` của nó — nếu **tất cả** task tiên quyết (theo `task_template_id` tương ứng trong cùng journey) đã `DONE` → chuyển task đó sang `READY`. Đây là phép **AND** đúng P0A D8.

## 3. API

| Route | Việc | Response |
|---|---|---|
| `GET /api/v1/portal/me/journey` | Trả journey đang hoạt động của chính user (tự tạo nếu chưa có, từ template `PUBLISHED` khớp `team_id` của user hoặc `team_id IS NULL`) | `EmployeeJourneyResponseDTO` — danh sách task kèm `status`, `title`, `completed_at` |
| `POST /api/v1/portal/me/tasks/{task_id}/complete` | Đánh dấu hoàn thành 1 task của chính user | `EmployeeTaskResponseDTO` |

Cả hai chỉ cho `get_current_user` (mọi role đăng nhập), **không dùng `require_role`** — đây là API của chính nhân viên, không phải API quản trị. Kiểm quyền thật sự nằm ở chỗ: task/journey phải thuộc đúng `user.id` đang gọi (404 nếu không phải của mình — không lộ có tồn tại hay không, tương tự cách `auth_service` xử lý).

- `backend/src/dto/response/portal_response_dto.py` — `EmployeeTaskResponseDTO`, `EmployeeJourneyResponseDTO`.

## 5. Definition of Done

- [ ] Test: journey chưa có → gọi `GET /me/journey` → tự tạo, task không phụ thuộc là `READY`, task có phụ thuộc là `LOCKED`.
- [ ] Test: hoàn thành task `READY` → `DONE`; task phụ thuộc nó (nếu chỉ phụ thuộc đúng task này) tự chuyển `READY`.
- [ ] Test: hoàn thành task đang `LOCKED` → 409 `TASK_LOCKED`.
- [ ] Test: hoàn thành lại task đã `DONE` → 200 idempotent, không lỗi.
- [ ] Test: task có 2 tiên quyết, mới xong 1 → vẫn `LOCKED` (đúng AND).
- [ ] Test: gọi API với task/journey của người khác → 404.
- [ ] `ruff check` + `ruff format` + `mypy` sạch.
- [ ] Chạy qua Docker (rebuild backend, test thật trên PostgreSQL container) — không chỉ venv local.
